# 使用说明

适用工作流：`.github/workflows/session.yml`
依据设计：`.team/specs/项目设计书-20261109-v3.md`（v3）

## 一、前提

| 项 | 要求 |
| --- | --- |
| 中继 | `relay.wuge.fun` 已按 v3 部署，`22` 可连 |
| 仓库变量 | `UPTERM_RELAY_KNOWN_HOST`：中继主机 known_hosts 行（公钥，防中间人） |
| 仓库变量 | `WEB_TERMINAL_BASE_URL`：网页终端静态页地址（不含任何会话参数） |
| 仓库变量 | `WEBAUTHN_CREDENTIAL_ID`：公钥凭据标识（公开标识，非秘密） |
| 可选变量 | `UPTERM_DIRECT_ENDPOINT`：直连候选对端 `host[:port]` |
| GitHub 账号 | `itwuge` 已登记 SSH 公钥；未登记则作业直接失败 |

缺任一必需变量，作业在「校验入口与前置配置」步骤即失败并列出缺失项。

## 二、两个触发入口

### 入口 1：workflow_dispatch（页面按钮）

Actions → 选择「调试会话」→ Run workflow → `start_session` 勾为 true → 运行。
默认 false，不勾选不建会话。

### 入口 2：repository_dispatch（关键词触发）

```bash
gh api repos/<owner>/<repo>/dispatches \
  -f event_type=start-session \
  -f client_payload[keyword]=start-session
```

- `event_type` 与 `client_payload.keyword` 两处都必须是 `start-session`，作业内会二次校验。
- 调用凭据需仓库 `Contents: write`（classic token 为 `repo`）。
- 该事件固定使用默认分支上的工作流。
- 发起者必须是 `itwuge`；`github.event.sender.login` 的语义 `[待真机确认]`。

两个入口落到**同一个 job、同一组步骤**，不存在两套会话逻辑。

## 三、连接顺序（先打洞、失败回落中继）

1. 阶段一：尝试直连（打洞）。托管 runner 无入站端口，通常没有可用对端地址，按判失败条件①直接进入阶段二；配置了 `UPTERM_DIRECT_ENDPOINT` 时只做 5 秒 TCP 可达性探针。
2. 阶段二：回落中继转发。回落**不重建会话**，`session_id` 保持不变，用户无需重新获取连接信息。
3. 看日志里的 `path_mode` 判断当前走的哪条路：`direct` 为直连，`relay` 为中继。
4. 在 GitHub 托管 runner 上，预期结果就是 `path_mode=relay`。
5. 用户可见提示固定两句，原文如下：
   - `直连已建立（直连）`
   - `直连未建立，已切换到中继转发`

> 直连分支的判定目前是 TCP 可达性探针，数据面是否真的直连 `[待真机确认]`；托管 runner 上不构成能力承诺。

## 四、日志里看哪几行

1. 「判定连接路径」步骤：上述两句提示之一。
2. 「输出路由字段」步骤（同时写入作业摘要）：9 行 `key=value`，字段固定为

   ```text
   relay_host / port / session_id / ssh_user / pubkey_fingerprint
   expires_at / web_url / pubkey_credential_id / path_mode
   ```

3. 9 行均为可公开展示的路由元数据，不做掩码；出现 `***` 即视为异常，需上报。
4. 「准备共享终端」步骤：共享终端是否就绪。

## 五、怎么连进去（SSH）

```bash
ssh <session_id>@relay.wuge.fun
```

- 若私钥不在默认路径，加 `-i <私钥路径>`。
- 上游当前连接串含 ticket 片段，属上游凭据，本工作流不写入任何字段；`session_id` 只是路由标识，单独拿到没有你的私钥进不来。
- 连上后可直接执行 `make menuconfig` 一类交互命令。

## 六、网页入口

- 日志中 `web_url` 形如 `<WEB_TERMINAL_BASE_URL>#session_id=<session_id>`：会话参数放在片段里，不进入浏览器请求行与服务端访问日志。
- 网页与 SSH 进入的是同一 `session_id` 的同一会话路由；共享终端由「准备共享终端」步骤提供（tmux 会话 `actssh`）。
- 网页端需设备侧公钥完成认证后放行，`pubkey_credential_id` 为对应的公钥凭据标识。
- 前端与准入校验由 P07/P08 落地；网页地址格式、桥接接入同一 socket 的方式 `[待真机确认]`。

## 七、结束与时限

| 操作 | 结果 |
| --- | --- |
| SSH 会话内 `exit` | 会话结束，两个入口同时失效 |
| 会话内 `touch $GITHUB_WORKSPACE/continue` | 作业继续执行 |
| 无人接入 | 10 分钟（`wait-timeout-minutes`）后自动结束 |
| 作业上限 | 45 分钟；`expires_at` 按此上限推算，误差为前置步骤耗时 |

## 八、安全约定

- 日志、制品、构建摘要、仓库中不得出现私钥、口令、一次性 token、GitHub token。
- 9 项路由字段不得掩码，路由字段不得取自 secrets。
- 会话标识可出现在日志，但不得作为唯一认证手段。
- 中继侧不保存用户凭据；重启即清空路由。
