# 使用说明

适用工作流：`.github/workflows/session.yml`（job 内只保留一步调用根目录 `action.yml`；会话逻辑统一在 Action 与 `scripts/action/`，与 `examples/`、可复用工作流共用）
依据设计：`.team/specs/项目设计书-20261109-v3.md`（v3）

## 一、前提

| 项 | 要求 |
| --- | --- |
| 中继 | `ssh.wuge.fun:2222`（uptermd 监听 2222，22 是宿主系统 sshd）；`relay.wuge.fun` 不再使用，未配 DNS |
| 仓库变量 | `UPTERM_RELAY_KNOWN_HOST`：中继主机 known_hosts 行（公钥，仅用于防中间人，不作为授权依据） |
| 仓库变量 | `WEB_TERMINAL_BASE_URL`：网页终端站点根地址，填 `https://wuge.fun`，不要带 `/t/` 或任何会话参数 |
| 仓库变量（可选） | `WEBAUTHN_CREDENTIAL_ID`：公钥凭据标识（公开标识，非秘密）。由浏览器在设备上注册时生成，无法预置；为空时该字段输出 `unset`，SSH 通道照常运行 |
| 仓库变量（可选） | `WEB_BRIDGE_BASE_URL`：网页桥接站点根，填 `wss://wuge.fun`（工作流自动补 `/runner`，也可直接填 `wss://wuge.fun/runner`）；完全不填时按 `wss://wuge.fun` 处理 |
| 仓库变量（可选） | `WEBAUTHN_ALLOWED_CREDENTIALS`：网页准入允许清单，单行 JSON 数组，每项只含 `credential_id`、`public_key`（COSE 公钥的 base64url）与可选 `transports`，均为公开信息。未配置时网页通道不可用；配置为空数组 `[]` 且开放注册时按自举模式运行（见 6.1） |
| 可选变量 | `UPTERM_DIRECT_ENDPOINT`：直连候选对端 `host[:port]` |
| GitHub 账号 | `itwuge` 已登记 SSH 公钥；未登记则作业在取公钥阶段直接失败 |

缺任一必需变量，作业在 Action 的「校验入口与前置配置」步骤失败并列出缺失项。

## 二、两个触发入口

### 入口 1：workflow_dispatch（页面按钮）

Actions → 选择「调试会话」→ Run workflow → `start_session` 勾为 true → 运行。
默认 false，不勾选不建会话。

### 入口 2：repository_dispatch（关键词触发）

```bash
gh api repos/<owner>/<repo>/dispatches \
  -f event_type=start-session \
  -f client_payload[keyword]=start-session
```

- `event_type` 与 `client_payload.keyword` 两处都必须是 `start-session`，作业内二次校验。
- 调用凭据需仓库 `Contents: write`（classic token 为 `repo`）。
- 该事件固定使用默认分支上的工作流。
- 发起者必须是 `itwuge`；`github.event.sender.login` 的语义 `[待真机确认]`。

两个入口落到**同一个 job**，job 内只有一步调用 Action，不存在两套会话逻辑。

## 三、连接顺序（先打洞、失败回落中继）

1. 阶段一：尝试直连（打洞）。托管 runner 无入站端口，通常没有可用对端地址，按判失败条件①直接进入阶段二；配置了 `UPTERM_DIRECT_ENDPOINT` 时只做 5 秒 TCP 可达性探针。
2. 阶段二：回落中继转发。回落**不重建会话**，`session_id` 保持不变，用户无需重新获取连接信息。
3. 看日志里的 `path_mode` 判断当前走的哪条路：`direct` 为直连，`relay` 为中继。
4. 在 GitHub 托管 runner 上，预期结果就是 `path_mode=relay`。
5. 网页入口地址不随路径切换变化，始终是 `https://wuge.fun/t/<session_id>`；回落中继不换地址、不改会话标识。
6. 用户可见提示固定两句，原文如下：
   - `直连已建立（直连）`
   - `直连未建立，已切换到中继转发`

> 直连分支目前只用 TCP 可达性探针判定，数据面是否真的直连 `[待真机确认]`；托管 runner 上不构成能力承诺。

## 四、日志里看哪几行

1. 「校验入口与前置配置」步骤（内含直连 TCP 探针）：上述两句提示之一。
2. 「输出路由字段」步骤（同时写入作业摘要）：9 行 `key=value`，字段固定为

   ```text
   relay_host / port / session_id / ssh_user / pubkey_fingerprint
   expires_at / web_url / pubkey_credential_id / path_mode
   ```

3. 9 行均为可公开展示的路由元数据，不做掩码；出现 `***` 即视为异常，需上报。
4. 「启动会话」步骤：确认共享终端已就绪（tmux 会话 `actssh` 由托管命令 `scripts/action/hosted-command.sh` 拉起并常驻）。
5. 「启动网页桥接」步骤：`网页通道已就绪：runner 已反连 …/runner/<session_id>，等待浏览器注册与准入`；不可用时为 `失败[阶段 bridge-connect|bridge-register|bridge-admission]：…；网页通道不可用，SSH 通道不受影响`。
6. 客户端自身的原始输出不打印、不进摘要、不进制品，只写入运行器临时文件、解析后立即删除。
   v0.41.1 的连接串里没有 ticket：`ssh_user` 取连接串用户位，`session_id` 恒为它冒号前的片段；冒号后是路由节点编码（embedded 模式），属可公开的路由信息。2026-11-09 真机实测：`-o json` 顶层共 33 个键，无 ticket/token 类字段，原始 stdout/stderr 中 ticket 出现 0 次；登录名形如 `<sessionId>:<base64(节点地址)>`，冒号前 20 位与 JSON `sessionId` 完全一致，冒号后为带 `=` 填充的标准 base64，解码后是 IPv4:端口形式的节点地址。

## 五、怎么连进去（SSH）

```bash
ssh -p 2222 <ssh_user>@ssh.wuge.fun
```

- 主机与端口取日志字段 `relay_host`／`port`，当前为 `ssh.wuge.fun`／`2222`。

- `ssh_user` 用日志里那行，不要自行拼接。v0.41.1 的登录名在 embedded 路由模式下形如 `<session_id>:<节点编码>`，只写 `session_id` 通常会被中继拒绝（源码 `routing/encoding.go` 的 `Decode` 要求带冒号）。
- 若私钥不在默认路径，加 `-i <私钥路径>`。
- 访客认证由 runner 侧闸门完成：只有 `itwuge` 在 GitHub 上登记的公钥被写入本次会话的授权清单，清单随作业销毁。中继侧 `UPTERMD_AUTHORIZED_KEYS` 只拦宿主注册，不拦访客（2026-11-09 实测：中继白名单外的访客公钥仍可登录，runner 清单外的访客被拒）。
- `session_id` 只是路由标识；能否进入由 runner 侧闸门决定。闸门未开启时任何私钥都可加入（2026-11-09 实测：临时生成的 ed25519 密钥即可登录）；闸门开启时只认清单内公钥，只有 `session_id` 而没有对应私钥进不来。
- 连上后可直接执行 `make menuconfig` 一类交互命令。

## 六、网页入口

### 6.1 启动条件

| 条件 | 说明 |
| --- | --- |
| 中继桥接进程 | 生产机上的 `actssh-web-bridge.service` 已部署并监听（nginx 容器可达的内网地址），未部署时网页通道必然失败 |
| nginx location | `wuge.fun` 的 443 server 块已 include `/ws/` 与 `/runner/` 两个 location，且 WS Upgrade 正常 |
| `WEB_BRIDGE_BASE_URL` | 可留空（按 `wss://wuge.fun` 处理）或填 `wss://wuge.fun`；只允许站点根或 `/runner` 终点 |
| `WEBAUTHN_ALLOWED_CREDENTIALS` | 可为空数组 `[]`：此时必须同时开放注册，按「自举注册」运行——本会话只接受**首个**注册请求，成功后立即绑定，同一会话内后续注册一律拒绝。非空数组时行为不变（仍需开放注册才可登记新凭据）。缺失或 JSON 非法时准入拒绝启动 |
| `WEBAUTHN_CREDENTIAL_ID` | 可留空；为空时准入开放注册引导（`--allow-registration`），由浏览器首次注册生成 |
| runner 依赖 | 「启动网页桥接」步骤在 `RUNNER_TEMP` 建虚拟环境，同时安装 `scripts/requirements-web-bridge.txt`（`websockets==10.4`）与 `scripts/requirements-web-admission.txt`（`fido2==2.2.1` 等），不污染宿主 Python |

桥接在「暂存路由字段」之后、`等待会话结束` 之前以**后台进程**启动，与 SSH 反连并行，不阻塞会话等待；两个入口共用同一 `session_id` 与同一 tmux 会话。

### 6.2 失败表现

失败一律显式打印 `失败[阶段 bridge-xxx]：…；网页通道不可用，SSH 通道不受影响`，并附 `::warning::` 注解；**作业不会因此失败，SSH 入口照常可用**。阶段名固定三档：

| 阶段 | 触发 |
| --- | --- |
| `bridge-connect` | 基地址非法、依赖安装失败、无法建虚拟环境、反连不可达/握手失败/超时、连接被关闭 |
| `bridge-register` | 桥接以 `ROUTE_CONFLICT` 拒绝注册（同会话已有 runner） |
| `bridge-admission` | 允许清单缺失或非法、准入子进程无法启动或非零退出 |

桥接进程本身按 `start_web_bridge.py` 契约非零退出（1 连不上或被拒、2 参数或运行错误），工作流读取其单行 JSON 的 `data.stage` 与 `error_code` 后映射为上表阶段名。20 秒内未观测到 `connected`/`admission.started` 事件时打印「网页通道状态待确认」。

### 6.3 排查顺序（固定三段）

1. **先看桥接注册**：日志 `网页通道已就绪…` 是否出现；否则看 `bridge-connect`/`bridge-register`。`bridge-connect` 多为中继桥接未部署、nginx `/runner/` 未生效或 `WEB_BRIDGE_BASE_URL` 不对；`bridge-register` 说明同会话已有 runner 反连（多半上一次会话未清理干净）。
2. **再看准入**：`bridge-admission` 表示允许清单缺失/非法，或准入进程退出。核对 `WEBAUTHN_ALLOWED_CREDENTIALS` 是否为合法单行 JSON 数组（允许为空数组 `[]`，此时走自举注册）、条目是否含 `credential_id` 与 `public_key`；非空清单却连不上时看是否误把自举当成常态。
3. **最后看浏览器**：前两段都正常仍进不去，再查浏览器侧——WebAuthn 注册/断言、`https://wuge.fun/t/<session_id>` 页面、`wss://wuge.fun/ws/<session_id>` 是否 101。

### 6.4 入口约定

- 日志中 `web_url` 固定形如 `https://wuge.fun/t/<session_id>`（即 `<WEB_TERMINAL_BASE_URL>/t/<session_id>`）：会话标识放在路径里，与 tmate 的 `/t/<id>` 一致，不使用 `?session=` 查询串，也不使用 `#session_id=` 片段。
- 打开 `https://wuge.fun/t/<session_id>` 即进入该会话的网页终端，无需再手工拼接或改地址。
- 首次打开会引导注册本设备通行密钥（WebAuthn）；注册成功后同一浏览器再打开同类连接串会直接进入，只需注册一次。页面会明确写出「一次注册，之后直接进」，未注册不是故障。
- 会话存活期内关掉页面或断网，重新打开同一链接可以再次进入（已注册设备直接验签进入）；已准入的连接再收到 `authBegin` 会重新签发一次性挑战，不会因为「进过一次」而失效。
- 会话不存在、已过期或路由已回收时，页面给出可读提示（例如「会话不存在或已结束」），不会只抛错误码；此时需向发起者索取新的连接串。
- 网页与 SSH 进入的是同一 `session_id` 的同一会话路由；共享终端是 tmux 会话 `actssh`，由托管命令 `scripts/action/hosted-command.sh` 常驻 attach（`while :; do tmux attach-session -t actssh; sleep 1; done`），窗口内是 `while :; do bash -l; done`。因此访客断开、`exit` 或 `Ctrl-D` 都不会让会话结束，桌面状态保留，可反复进入（见第七节）。
- 网页端需设备侧公钥完成认证后放行，`pubkey_credential_id` 为对应的公钥凭据标识；首次运行必为 `unset`（设备尚未注册），属正常值，不算字段缺失。
- 前端由 P07 实现；桥接与准入的真实域名链路（wss 可达、nginx Upgrade、WebAuthn 真实验签）`[待真机确认]`。

### 6.5 已知残余风险：空清单自举注册

- 允许清单为空数组 `[]` 且开放注册时，**首个**完成的注册请求即被接受。该窗口期内，凡是拿到会话链接（`https://wuge.fun/t/<session_id>`）的人都能成为这把凭据的持有者；会话链接在此期间等同门票，不具备「只有本人能进」的保证。
- 窗口随会话结束立即关闭：注册成功即绑定到本次 `session_id` 并拒绝同一会话后续注册；会话结束、runner 断开或准入进程退出后，绑定与凭据一并消失，不写仓库变量、不落盘、不打印。
- 需要「只有指定设备能进」时，不要使用空数组；改为在 `WEBAUTHN_ALLOWED_CREDENTIALS` 预置该设备的公开凭据后运行。
- 该风险在 `.team/records/设计更正-网页桥接落点-20261109.md` 的「已知残余风险」中同步记录。

## 七、会话生命周期

**一句话：会话存活期内可反复进入，空闲或超时后结束。**

### 7.1 保持

| 操作 | 结果 |
| --- | --- |
| SSH 里 `exit` / `Ctrl-D` | **只结束当前 shell**，tmux 窗口随即起一个新 shell，会话保持；用同一连接串可立刻重连 |
| 关掉客户端、断网、`kill` 本地 ssh | 连接断开，会话保持；重连后看到同一个 tmux 终端（滚动区、当前目录、运行中的前台进程都在） |
| 网页关闭标签页 / 断网 | 准入与中继路由保持；重新打开同一 `https://wuge.fun/t/<session_id>`，已注册设备直接进，同见 6.4 |
| 多入口并行 | SSH 与网页进入的是同一个 `tmux` 会话 `actssh`，任意先后重连看到的是同一终端状态 |
| 会话内 `touch $GITHUB_WORKSPACE/continue` | 作业继续执行，会话不受影响 |

重连**不需要**重新触发 workflow，也不需要新的连接串。

### 7.2 结束（仅这四种）

| 触发 | 判据 | 结果 |
| --- | --- | --- |
| 显式结束 | 在会话内执行 `upterm session stop actssh`（或由 Action 的收尾步骤执行同一命令） | `upterm session wait` 返回，作业进入收尾；两个入口同时失效 |
| 空闲超时 | 无人连接累计超过 `idle-minutes`（默认 **10** 分钟），SSH 与网页**合计**计数 | 由 runner 侧看门狗主动 `stop`，日志写 `::warning::空闲超时结束会话` |
| 会话上限 | `session-minutes`（默认 45） | 「等待会话结束」步骤按超时终止，作业失败并收尾 |
| 作业上限 | 固定 55 分钟（含安装与清理） | GitHub 取消作业，收尾照常执行 |

- **空闲默认 10 分钟的理由**：调试会话通常有人值守，10 分钟无人在连基本等于已弃用；同时压缩 runner 占用与暴露窗口，并把爆破尝试的滑窗同值（见 7.3），便于统一解释。取值可调（正整数，且不得超过 `session-minutes`），需要长时间挂着编译时把它调大，或先连进去跑着。
- 空闲判定口径：SSH 侧取 `upterm` 日志中该 `session_id` 的 `Client joined` 减 `Client left`；网页侧取准入进程在作业临时目录写的在连标记。两者之和为 0 才开始计时。`--join-timeout` 不参与空闲判定——它在首个访客加入后永久解除，不能当空闲依据。

### 7.3 失败尝试上限（防爆破）

| 通道 | 上限 | 时间窗 | 超限后 |
| --- | --- | --- | --- |
| 网页（WebAuthn 断言/注册） | 单连接 3 次，全会话 10 次 | 10 分钟滑窗 | 关闭该连接，窗口内继续拒绝新的准入请求；**不结束会话**，窗口过后可再试 |
| SSH | 不受 runner 控制 | — | 访客认证在中继侧完成，runner 只看得到 `Client joined`/`Client left`，**看不到认证失败**（2026-11-09 实测：2 次错误公钥后日志 `unauthorized public key` 计数仍为 0）。需要 SSH 侧限速请在 `uptermd` / 前置网关配置，例如按来源 IP 限制连接速率与并发 |

失败尝试上限与「首次成功即消费」无关：成功进入不消耗任何额度，也不影响后续重连；额度只在失败时扣减。

### 7.4 结束后重连

会话一旦结束，该 `session_id` 的路由即被回收：SSH 重连得到 `Permission denied`（exit 255），网页提示「会话不存在或已结束」。此行为是硬约定，不会因重连次数或时间而放宽。需要继续干活请重新触发一次 workflow，拿新的连接串。

收尾由「等待会话结束」步骤的退出钩子与「收尾清理」步骤共同保证：停 `upterm` 会话、杀看门狗与网页桥接/准入进程、关 `tmux` 会话、删除临时目录（含授权清单与自举回写的公开凭据）。

## 八、失败时怎么读日志

失败行统一为 `失败[阶段 xxx]：…`，只给阶段名与原因，不回显客户端原始输出。

| 阶段 | 含义 |
| --- | --- |
| `precheck` | 入口校验或必需仓库变量缺失 |
| `fetch-keys` | 取不到 `itwuge` 的公钥，或指纹计算失败 |
| `install-client` | upterm 客户端下载失败、校验和不符或无法执行 |
| `start-session` | 客户端启动会话失败（进程异常退出） |
| `linking` | 未取得连接串，或 JSON 里 `status` 不是 `ready` |
| `parse-connection` | 取不到 SSH 登录名、`sessionId` 缺失，或登录名与 `sessionId` 不一致 |
| `shared-terminal` | 启动后 10 秒内未发现 tmux 会话 `actssh`（托管命令未起来） |
| `session-wait` | `upterm session wait` 返回 125（结局不可知），或返回后会话状态仍为 `ready`/`starting` |
| `bridge-connect` | 网页桥接反连失败（基地址非法、依赖缺失、不可达/握手失败） |
| `bridge-register` | 网页桥接注册被拒（`ROUTE_CONFLICT`，同会话已有 runner） |
| `bridge-admission` | 网页准入无法启动（允许清单缺失/非法或准入进程退出） |

## 九、安全约定

- 日志、制品、构建摘要、仓库中不得出现私钥、口令、一次性 token、GitHub token。
- 登录名冒号后的路由节点编码属路由信息，不属凭据；`ssh_user` 必须原样保留完整登录名，日志只输出 9 项白名单字段。
- 9 项路由字段不得掩码，路由字段不得取自 secrets。
- 中继侧不保存用户凭据；重启即清空路由。
- 客户端二进制按固定版本与固定 SHA-256 校验后使用。
