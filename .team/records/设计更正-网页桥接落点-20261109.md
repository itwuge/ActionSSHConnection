# 设计更正：网页通道桥接落点（2026-11-09）

| 项目 | 内容 |
|---|---|
| 文件性质 | 设计更正，不改已有技术结论；SSH 通道结论不变，网页通道仅修正「字节流如何到达 runner」这一落点 |
| 依据 | 真实 runner 已跑通 SSH 通道（run `42619914816`：9 字段齐全、登录到正确 runner、回收与重连被拒均通过）；网页通道在真机联调中暴露结构性缺口 |
| 主笔 / 会签 / 拍板 | M03 架构师 / P07、P08、P04、O01 / M01 |
| 结论 | 主案：中继侧新增无状态网页桥接进程 + runner 第二条主动反连 WS；备选：runner `ssh -R` 回环端口 + nginx 固定转发。方案二（改用 upterm SSH-over-WS）淘汰 |
| 历史版本 | 设计书 v1、v2 保留不改；本文件与设计书 v3 的对应章节同步，需求条目另出 v5 |

## 一、缺口事实（均已核实）

| 序号 | 事实 | 影响 |
|---|---|---|
| 1 | `uptermd` 只代理 SSH，不转发本项目自定义的 `authBegin` / `authChallenge` / `authAssertion` 帧 | 现行设计「浏览器自定义帧经中继 WS 直达 runner 侧 `web_admission.py`」不成立 |
| 2 | runner 侧 `scripts/web_admission.py` 通过 stdin/stdout 读写二进制帧；runner 不在公网、不开放入站端口 | 浏览器无法直接连 runner；必须由 runner 主动建立的反向通道承载字节流 |
| 3 | 生产机 443 由 `certbot-nginx` 容器统一终止 TLS；`ssh.wuge.fun` 已反代到 `172.17.0.1:8443`（uptermd 的 WS 端口，仅 docker 网桥可达） | 该 WS 端点承载的是 upterm 自己的 SSH-over-WS，与自定义帧协议不匹配；不能直接复用 |
| 4 | 现有前端按自定义帧协议实现；`WEBAUTHN_CREDENTIAL_ID` 已改为可选，首次为 `unset` | 前端帧协议不必推翻；缺口只在「帧到 runner」的传输路径 |
| 5 | SSH 通道已在真实 runner 通过判据一至四；网页通道尚未取得判据五、六、七的证据 | 本次只改网页通道承载方式，不回头改 SSH 结论，也不把网页通道写成已通过 |

## 二、红线与判定方法

| 红线 | 判定方法 | 本次结论 |
|---|---|---|
| 日志、制品、摘要、仓库四类载体零凭据；路由字段不得被掩码 | 对桥接/准入/前端代码与运行日志逐项检索私钥、口令、一次性 token、GitHub token；9 项字段原样可读 | 主案满足：桥接只按 `session_id` 配对，不解析帧、不打印负载；`session_id` 属路由信息 |
| runner 不开放入站端口；中继不持有用户私钥、口令、长期 bearer | 检查 runner 监听端口与中继文件/内存；检查中继是否保存任何用户凭据 | 主案满足：runner 主动出站；中继只存内存映射 |
| 会话结束即失效，浏览器不能用旧会话标识再次进入 | 结束会话后旧 `session_id` 重连必须被拒；新会话建立后旧标识也不得串入新会话 | 主案满足：runner 断开即删映射；旧标识无路由；新会话 `session_id` 随机且不复用 |
| 3 Mbps、2 vCPU 的中继不能引入重负载组件 | 资源上限、常驻内存、并发连接与磁盘写入逐项核算 | 主案满足：桥接为单进程异步字节转发，设 `MemoryMax`、`CPUQuota`、`TasksMax`，不落盘 |

## 三、三方案对比

| 维度 | 方案一：中继桥接 + 第二条反连 WS（主案） | 方案二：改用 upterm SSH-over-WS + 入站前关口（淘汰） | 方案三：runner `ssh -R` 回环端口 + nginx 固定转发（备选） |
|---|---|---|---|
| 做法 | nginx 把 `wss://wuge.fun/ws/<session_id>` 转到中继回环桥接端口；runner 另起一条出站 WSS 到 `wss://wuge.fun/runner/<session_id>`；桥接按 `session_id` 配对两条 WS，双向转发二进制帧；runner 侧把桥接连接接到 `web_admission.py` 的 stdin/stdout | 浏览器直接用 uptermd 的 SSH-over-WS；WebAuthn 关口移到入站前 | runner 用 `ssh -R 127.0.0.1:8790:127.0.0.1:8790` 把本机 WS 入口映射到中继回环；nginx 把 `/ws/<session_id>` 固定转到 `127.0.0.1:8790`；由 runner 侧 WS 入口校验 `session_id` 并接 `web_admission.py` |
| 认证验签落点 | runner 侧 `web_admission.py`，与 v3 一致 | 只能在三处：浏览器 JS（可绕过，淘汰）、中继 nginx `auth_request`（中继成为认证方，违反红线）、runner 侧（uptermd 已在更早层终结 SSH，进不到 runner） | runner 侧 `web_admission.py`，与 v3 一致 |
| 中继新增组件 | 一个小型桥接进程（Python asyncio，P04 主责）+ 一个 systemd 单元 + 两段 nginx location | 无新增桥接，但需改造 nginx 鉴权链或引入验签服务 | 无新增常驻进程；复用系统 sshd 的 `-R` 与 nginx |
| 是否要求凭据落中继 | 否；只存内存 `session_id → runner_ws`，重启即清空 | 若走 nginx `auth_request`，中继需保存挑战状态并验签，**是** | 否；中继只存 runner 服务公钥（允许），不存用户私钥 |
| runner 入站端口 | 不开放；runner 主动出站 443 | 不开放 | 不开放；runner 主动出站 SSH |
| 会话语义 | runner 断开即删映射；旧 `session_id` 无路由；新会话随机新标识 | 取决于关口实现；关口若在中继则状态与凭据问题无法回避 | 旧会话标识由 runner 侧 WS 入口按 `session_id` 拒绝；固定端口需防串会话 |
| 资源代价 | 单进程异步转发，内存上限 128 MiB、`CPUQuota=50%`、`TasksMax=64`；不落盘 | 若加验签服务反而更重；若只靠前端 JS 则无安全意义 | 最轻；但依赖中继 sshd 可被 runner 访问且允许 `-R` |
| 并发会话 | 支持多会话，按 `session_id` 配对 | 不适用 | 固定回环端口天然单会话；多会话需端口分配或复用，会引入状态 |
| 红线结论 | **满足** | **不满足**（要么可绕过，要么中继终结认证/持状态） | **满足，但条件成立**：需中继 sshd 可达并允许 `-R`，且单会话 |
| 主要代价 | 中继多一个常驻进程与一个 runner 注册端点；需防路由抢占与资源打满 | 推翻现有自定义帧与 runner 侧验签；且无合规落点 | 依赖宿主 sshd 配置；单会话；runner 侧需 WS 入口适配；nginx 固定端口无法按会话路由 |

## 四、选定方案与理由

### 4.1 主案：方案一（中继桥接 + 第二条反连 WS）

理由：

1. **不依赖宿主 sshd**。现有生产机的 443 已由 nginx 统一终止 TLS，runner 出站 443 已被 SSH 通道验证可用；方案一只复用这条路径，不需要额外确认 sshd 是否对外开放 `-R`。
2. **前端与准入进程改动最小**。自定义帧协议保留，`web_admission.py` 的 stdin/stdout 形态保留，`WEBAUTHN_CREDENTIAL_ID` 可选与首次 `unset` 的行为保留；只增加一条传输通道。
3. **认证仍在 runner 侧**。桥接只按 `session_id` 配对与转发，不解析帧、不验签、不判定；符合「中继不终结认证」。
4. **会话语义可直接验收**。runner 断开 → 桥接删映射并关闭浏览器连接；旧 `session_id` 无路由；新会话使用新的随机标识，旧标识不会串入。
5. **资源可控**。桥接是无磁盘的异步字节转发，单进程即可；资源上限写入 systemd，不引入数据库、消息队列或缓存服务。

### 4.2 备选：方案三（runner `ssh -R` 回环端口 + nginx 固定转发）

仅当主案被否决（例如不允许在中继新增任何自研进程）时启用。启用前必须确认：中继系统 sshd 可被 runner 访问、允许 `AllowTcpForwarding` 与 `-R`、回环端口绑定不对外、nginx 能把 `/ws/` 转到该回环端口、runner 侧有 WS 入口并校验 `session_id`。代价是单会话、固定端口、runner 侧多一层 WS 适配；不满足任一条即退回 SSH 单入口。

### 4.3 淘汰：方案二（改用 upterm SSH-over-WS）

淘汰原因：WebAuthn 关口若放浏览器 JS，直接连 WS 即可绕过；若放中继 nginx `auth_request`，中继必须保存挑战状态并验签，违反「不终结认证、不落盘状态、不持凭据」；若想放 runner，uptermd 已在更早层终结 SSH，自定义断言进不到 runner。三条路都不满足红线，故不采用。若将来 uptermd 提供可编程的入站前钩子，且钩子能把断言转给 runner 验签，可重新评估；当前标 `[待真机确认]`，不作承诺。

## 五、选定方案的接口变更

### 5.1 前端（P07）

| 项目 | 变更 |
|---|---|
| 帧协议 | 不变；继续使用 `web/src/protocol/frames.ts` 的 `authBegin` / `authChallenge` / `authAssertion` / `authResult` 与终端数据帧 |
| WS 地址 | `wss://wuge.fun/ws/<session_id>`；路径只带 `session_id`，不带 token、口令、公钥原文 |
| 凭据标识 | `WEBAUTHN_CREDENTIAL_ID` 继续可选；首次进入为 `unset`，走注册引导；注册后仅在本机保存公开的凭据标识，不保存私钥或断言 |
| 页面地址 | `https://wuge.fun/t/<session_id>`；不新增查询参数承载凭据 |
| 断线处理 | 收到 `UNKNOWN_SESSION` / `ROUTE_GONE` 时提示「会话已结束或不存在」，不自动用旧标识重试进入 |

### 5.2 中继桥接进程（P04 实现，O01 部署）

| 项目 | 变更 |
|---|---|
| 进程 | 新增 `scripts/bridge/relay_bridge.py`（Python 3.8+，asyncio + `websockets`），由 systemd 单元 `actssh-web-bridge.service` 拉起 |
| 监听 | 仅监听 `172.17.0.1:8081` 或 `127.0.0.1:8081`（二者择一，按 nginx 容器可达方式定）；不监听公网地址 |
| 端点 | `GET /ws/<session_id>`（浏览器，Upgrade: websocket）；`GET /runner/<session_id>`（runner 反向 WS） |
| 配对 | 内存字典 `session_id → runner_ws`；浏览器到达时若已有 runner 则附加，否则以 `UNKNOWN_SESSION` 关闭；runner 重复注册以 `ROUTE_CONFLICT` 关闭后者；runner 断开时以 `ROUTE_GONE` 关闭所有浏览器连接 |
| 转发 | 二进制帧原样转发，不解析、不改写、不落盘；不读取帧内容做日志；仅记录连接事件、字节计数与关闭码 |
| 上限 | 单帧上限 1 MiB；每会话浏览器连接上限 2；全局连接上限按 `MemoryMax=128M`、`CPUQuota=50%`、`TasksMax=64` 兜底；不写任何文件 |
| 重启语义 | 进程重启即清空全部配对；进行中的 WS 全部断开；不恢复、不重放 |
| 日志 | 只写 systemd journal 的连接元数据；不写帧负载、不写凭据；`session_id` 属路由信息，可原样记录 |

### 5.3 runner 侧（P08 入口，P04 提供 Python 客户端）

| 项目 | 变更 |
|---|---|
| 新增入口 | `start_web_bridge <session_id> <bridge_ws_base> <admission_cmd>`；`bridge_ws_base` 形如 `wss://wuge.fun/runner`；退出码 0 正常结束、1 连不上或被拒、2 出错；stdout 单行 JSON 五字段 |
| 反连 | runner 主动出站 `wss://wuge.fun/runner/<session_id>`；不监听任何入站端口；连接建立后把双向字节接到 `web_admission.py` 的 stdin/stdout |
| 准入进程 | `web_admission.py` 不改命令行契约；`--session-id` 仍由 runner 传入；`WEBAUTHN_CREDENTIAL_ID` 为空时走注册引导 |
| 失败处理 | 连不上桥接、收到 `ROUTE_CONFLICT`、准入被拒时，关闭连接并以退出码 1 返回；不得把失败原因写成含凭据的文本 |
| SSH 通道 | 不变；`start_web_bridge` 与 SSH 反连可并行，两个入口共享同一 `session_id` 与同一 tmux 会话 |

### 5.4 nginx 与部署（O01）

| 项目 | 变更 |
|---|---|
| nginx | 新增 `location /ws/` 与 `location /runner/`，`proxy_pass http://172.17.0.1:8081`；`proxy_http_version 1.1`、`Upgrade`/`Connection` 头、`proxy_buffering off`、`proxy_read_timeout` 不低于会话上限；TLS 仍由现有 `certbot-nginx` 终止 |
| nftables | 只允许 docker 网桥到 `8081`；不开放公网入站 |
| `deploy_relay.sh` | 新增桥接进程、systemd 单元、nginx 片段、日志上限与资源上限；保留原有幂等、失败即退出、不硬编码 |
| `check_relay_health.sh` | 新增「桥接监听存在」「重启后配对为空」「无会话文件」三项；原有 SSH 转发检查不变 |
| `bind_session_route` | 语义变更：不再由独立脚本绑定；由桥接进程按 `session_id` 在内存内完成。若保留该名称，只作为桥接内部函数，不作为对外脚本接口 |

### 7.3 风险

| 序号 | 风险 | 处置 |
|---|---|---|
| 10 | 桥接进程成为网页通道单点 | systemd 自动重启；桥接挂掉只影响网页入口，SSH 入口不受影响；不引入第二套桥接 |
| 11 | runner 注册端点被抢占（知道 `session_id` 即可先注册） | `session_id` 使用 256 位随机值；首个 runner 注册生效，后续以 `ROUTE_CONFLICT` 拒绝；属可用性问题，不构成认证绕过；必要时重触发换新标识 |
| 12 | nginx WS 超时/缓冲导致断流 | 明确 `proxy_read_timeout`、关闭缓冲、加心跳；真机确认前不写成已具备 |

### 7.4 已知残余风险（空清单自举注册）

| 项目 | 内容 |
|---|---|
| 背景 | 首次使用时不存在可预置的公开凭据，允许清单为空会使网页通道永远无法注册（先有鸡还是先有蛋）。 |
| 裁决 | 按 tmate 语义允许自举：允许清单为空数组 `[]` 且准入开放注册时，接受**首个**完成的注册请求，成功后立即把本次 `session_id` 绑定到该凭据；同一会话内后续注册一律以 `BOOTSTRAP_CONSUMED` 拒绝；非空清单行为不变。 |
| 残余风险 | 自举窗口期内，会话链接（`https://wuge.fun/t/<session_id>`）等同门票：任何拿到链接的人都能完成这一次注册并成为凭据持有者，此时不具备「只有本人能进」的保证。 |
| 窗口边界 | 首个注册成功即关闭；会话结束、runner 断开或准入进程退出后，绑定与凭据一并消失。凭据只存在于准入进程内存与浏览器 localStorage，不写仓库变量、不落盘、不打印。 |
| 日志 | 只增加一条 `admission.bootstrap_registered`，字段限定为 `session_id`、`credential_id_prefix`（前 8 位）、`registered_at`，不含公钥与断言。 |
| 处置 | 需要限定设备时不得使用空数组，改为预置该设备公开凭据；本风险同步写入 `docs/使用说明.md` 6.5 与 `deploy/README.md` 12.8，窗口随会话结束关闭的要求在真机判据五、六取证时一并核对。 |

## 八、回滚

| 步骤 | 内容 | 判据 |
|---|---|---|
| 1 | 停用 `actssh-web-bridge.service`，移除 nginx `/ws/` 与 `/runner/` 两个 location | 网页入口不可用，SSH 入口仍通过判据一至四 |
| 2 | 保留 `web_admission.py` 与前端代码，不删仓库文件；不清理任何用户数据（本方案不落盘） | 仓库无凭据；中继无新增文件 |
| 3 | 若桥接资源不可接受且方案三条件成立，再评估切换 `ssh -R`；否则网页通道顺延 | 回滚后 SSH 通道证据仍可复现 |

## 九、结论与未定项

- 选定主案：中继侧无状态桥接进程 + runner 第二条主动反连 WS；前端帧协议与 runner 侧验签不变。
- 备选：runner `ssh -R` 回环端口 + nginx 固定转发；仅在主案被否决且第 6 节条件全部成立时启用。
- 淘汰：方案二；若 uptermd 将来提供入站前钩子，可重新评估，当前不作承诺。
- 未定项：第 6 节 8 项全部标 `[待真机确认]`；未取得证据前，网页通道不得写成已具备能力，判据五、六、七记「未验证」。
