## 三、架构与目录

### 3.1 分层与依赖方向

| 项目 | 填写内容 |
|---|---|
| 分层 | 入口层（`.github/workflows/`）：触发与调用，不含部署逻辑；脚本层（`scripts/`）：中转部署、密钥轮换、会话与端口检查，可被入口层调用，不反向调用；前端层（`web/`）：浏览器侧终端与公钥认证，只与中转的 WS 端点通信，不直连 runner；中转层（宿主上的 systemd 单元与 nftables 规则）：无状态字节转发，无业务逻辑；文档层（`docs/`）：使用与运维说明；底座层（`.team/`）：规范与记录，不参与运行 |
| 依赖方向 | 允许：入口层 → 脚本层；前端层 → 中转层（仅 WS 字节流）；中转层 → runner 反向建立的隧道（被动使用，中继不主动连 runner）。禁止：脚本层 → 入口层；中转层 → 前端层（中继不主动推送业务消息，除连接关闭）；中转层 → runner 的业务协议解析；任何层 → 底座层；任何层 → 文档层 |
| 外部依赖清单 | GitHub Actions runner（ubuntu-latest，托管，MIT 平台服务，占用 Actions 分钟数）；`owenthereal/action-upterm`（固定 commit SHA，反连客户端动作，MIT）；`uptermd` 官方二进制（固定版本，MIT）；OpenSSH（Ubuntu 20.04 系统包，BSD）；systemd（LGPL）；nftables（GPL-2.0）；xterm.js 类前端库（P07 选型，MIT 候选）；阿里云成都 ECS（资源基线第一条，**需按四类升级处理·第 1 类：花钱或占用资源**）；GitHub Pages（静态前端托管，免费，**需按四类升级处理·第 2 类：对外承诺与合规**，公开发布静态页） |

### 3.2 双入口共享同一会话路由

| 项目 | 填写内容 |
|---|---|
| 通道数 | 两条并行入口：SSH 通道（v2 既有，结论不变）与网页通道（v3 新增） |
| 共享对象 | 同一会话的同一路由记录：`session_id` 为唯一键，中继内存中只维护 `session_id → runner 反向连接` 一条映射；两个入口进入的是**同一个终端进程** |
| 路由建立 | runner 主动反连中继并注册 `session_id`；中继只记录映射，不判定谁有权进入 |
| 路由回收 | 会话结束或中继重启，映射删除；不写盘、不归档 |
| `[意图]` 并发进入 | 两个入口同时进入同一会话属允许行为，表现为两个终端视图共享一个终端进程；该行为对 TUI 的使用影响 `[待真机确认]`，实测前不承诺可用 |

### 3.3 中继职责边界

| 做什么 | 不做什么 |
|---|---|
| 接受 runner 的反向连接并登记 `session_id → 连接` 的内存映射 | 不终结身份认证：不校验访客公钥、不验 WebAuthn 断言、不验客户端证书 |
| 接受浏览器到 WS 端点的连接，按 `session_id` 找到对应 runner 连接 | 不做访问判定：不维护访客白名单，不判断「谁可以进」 |
| 双向转发字节流（SSH 协议字节、WS 帧负载），不做应用层解析 | 不解析应用帧内容，不识别协议语义，不渲染终端 |
| 维持连接保活，在任一端断开时向另一端传播断开 | 不落盘会话状态：不写会话文件、不写审计账本、不写回放数据 |
| 终止传输层 TLS（`wss://`），仅做加密与证书出示 | 不存任何用户凭据：无私钥、无口令、无一次性 token、无长期 bearer；仅可存公钥/公钥指纹用于路由绑定 |
| 记录连接元数据（地址、端口、`session_id`、指纹、时间）到系统日志 | 不限流、不做审计结论：限流与连接数控制下沉到 `nftables` 与 systemd，审计由系统层与 runner 侧承担 |
| 进程重启即清空全部映射 | 不保证重启期间会话连续：重启即断开，属预期行为 |

### 3.4 三方各持有什么

| 持有物 | 浏览器侧（用户设备） | runner 侧 | 中转侧 |
|---|---|---|---|
| 用户私钥 | **持有**：WebAuthn 平台密钥或设备密钥，永不出设备 | 不持有 | 不持有 |
| 用户公钥 / 公钥指纹 | 持有（公钥） | 持有：用于验签的允许清单，随作业销毁 | 仅在路由绑定时使用公钥指纹标识，不参与判定 |
| 会话地址与 `session_id` | 持有（日志给出） | 持有（生成方） | 持有：内存映射的键 |
| 终端进程 | 不持有 | **持有**：runner 内唯一实例 | 不持有 |
| 访客 SSH 公钥 | 持有（用户设备） | 持有：内嵌 sshd 的 `authorized_keys`，作业结束销毁 | 不持有 |
| 服务身份密钥（中转 host key / TLS key） | 信任其指纹（`known-hosts`、证书校验） | 不持有 | **持有**：`0600`，登记可轮换 |
| 会话内容 | 屏幕上可见 | 进程内可见 | 不持有、不留存 |
| 审计证据 | 无 | 作业日志（作业结束即销毁） | 系统层连接元数据（无内容、无身份结论） |

失去中继侧审计后的补偿与残余风险：

| 项 | 补偿手段 | 残余风险（照实记录） |
|---|---|---|
| 谁连过中转 | `nftables` 规则计数 + journald 连接元数据（源地址、时间、`session_id`） | 无法从日志判断「进入者身份」，只能看到连接事实 |
| 认证是否成功 | runner 内嵌 sshd 日志与网页准入日志，均只在作业运行期存在 | 作业结束即销毁，事后无法复盘具体认证过程 |
| 是否有异常流量 | `nftables` 计数突增 + systemd 资源指标 | 无内容级检测能力，中继不识协议 |
| 跨会话关联 | 无 | 中继无状态，无法把多次会话串起来；这是降级的直接代价，不设替代方案 |
| 浏览器侧行为 | 依赖设备自身安全 | 服务端无任何浏览器侧审计，`[意图]` 接受该风险 |

### 3.6 网页通道与公钥型认证

| 项目 | 填写内容 |
|---|---|
| 前端 | `web/` 下 xterm 类终端页；静态托管候选为 GitHub Pages（对外发布，需四类升级第 2 类放行）；前端只做终端渲染与本地签名，不含业务判定 |

| 认证方式（一期取定） | **WebAuthn 应用层挑战**：挑战与断言经 WS 字节流转发，由 runner 侧进程验签；私钥在设备内；中继不参与验签。选它的理由：认证判定留在 runner 侧，与「中继不终结认证」一致 |
| `[已否决]` 一期做法 | 客户端证书 mTLS 由中继在 TLS 层验证——该做法要求中继持有 CA 并做判定，与无状态只转发冲突；若将来要做，必须改成 TLS 透传或由 runner 侧终结，二者均 `[待真机确认]`，本期不采用、不承诺 |
| `[意图]` 公钥存放 | 中转只允许存公钥指纹（用于路由绑定标识），不存任何私钥；runner 侧保存验签允许清单，随作业销毁 |
| `[已否决]` | 网页 URL 带一次性 token；口令认证；OAuth `client_secret` 落中转；长期 bearer |

### 3.7 日志字段与「不得掩码」「四类载体零凭据」的关系

| 项目 | 填写内容 |
|---|---|
| 字段白名单（9 项） | 中转地址、端口、会话标识、SSH 用户名、公钥指纹、到期时间、网页地址、公钥凭据标识、**当前路径**（`path_mode`，取值 `direct` 或 `relay`） |
| 与「不得掩码」的关系 | 9 项均属可公开展示的元数据，**任一字段被掩码成 `***` 即判据一、判据五或判据七失败**；新增的网页地址、公钥凭据标识与当前路径同样不得掩码。掩码规则不得把整行路由信息一并抹掉 |
| 与「四类载体零凭据」的关系 | 私钥、口令、一次性 token、GitHub token 一律不得出现在日志、制品、构建摘要、仓库；网页地址本身不含凭据，若地址中出现任何凭据参数即判违规；公钥与公钥指纹属允许展示项，不构成凭据；mTLS 私钥若将来引入，只允许存在于设备，不得进入四类载体 |
| 交叉约束 | 判据五（网页入口）与判据六（中继无状态）不能以牺牲判据一（字段可读）为代价；若脱敏规则与字段可读冲突，以字段可读优先，凭据类内容一律在设计阶段就不产生 |

### 3.8 降级对既有内容的影响

| 既有项 | 影响 | 处置 |
|---|---|---|
| `uptermd` 是否仍作转发进程 | **仍作转发进程**，但停用其准入能力：不再依赖 `authorized_keys` 白名单与 `limit-access-to-users` 做访客准入，准入改由 runner 侧完成 | `[待真机确认]`：uptermd 能否在准入能力关闭/不启用的情况下仅做转发；若不支持，候选是通用 WS/TCP 中继（`nftables` + 最小转发器），届时需重新评估是否引入新语言负责人，**本期不定** |
| 中转 host key | 角色变化：由「服务身份 + 准入依据」降为「**仅服务身份**」，用途是防中间人，不再作为授权凭据使用 | 保留，登记、`0600`、可轮换 |
| `known-hosts` 与仓库变量 `UPTERM_RELAY_KNOWN_HOST` | 性质变化：仍必需，但校验目的从「确认被授权的端点」改为「确认没有中间人」 | 保留变量与校验，文档中改写用途说明 |
| `/etc/uptermd/authorized_keys` | 不再是准入依据 | 作废其白名单语义；文件去向 `[待真机确认]`（可留档或删除，不得作为判定源） |
| `limit-access-to-users: itwuge` | 不再承担准入；SSH 用户白名单移入 runner 内嵌 sshd 的 `authorized_keys` | 工作流参数保留与否 `[待真机确认]`；不得在文档中继续称其为准入手段 |
| `wait-timeout-minutes` / 单步与作业超时 | 语义不变（无人接入超时与会话总时长仍分离），仍由 runner 侧计时 | 保留 |

### 3.9 连接建立策略：默认优先打洞，中继兜底

| 项目 | 填写内容 |
|---|---|
| 策略 | 会话建立分两阶段：先尝试两端直连（打洞），失败即回落中继转发；`session_id` 在两个阶段不变，用户侧连接目标只有一个入口地址 |
| 阶段一 直连打洞 | 条件：两端均能获得可达的对端地址（自建 runner 有入站端口，或双方 NAT 类型允许）。`[待真机确认]` |
| 超时 | 打洞阶段整体超时上限候选 5 秒（可配置），**具体值待实测确定**；超时即判失败，不反复重试 |
| 判失败条件 | 任一条成立即判失败：① 无可用对端地址；② 协商阶段无响应或响应超时；③ 打洞后握手未在超时内完成；④ NAT 类型不兼容；⑤ 路径稳定性检测未通过（`[待真机确认]` 判定方法） |
| 回落动作 | 立即切中继转发，不重建 `session_id`、不重置会话，用户无需重新获取连接信息 |
| 判成功的留痕 | 日志记录 `path_mode=direct` 与直连对端地址；不记录任何密钥材料 |
| 用户可见提示 | 固定两句，只描述路径状态、不含任何凭据：「直连已建立（直连）」与「直连未建立，已切换到中继转发」。提示中不得出现私钥、口令、一次性 token、会话密钥或完整指纹以外的凭据；允许出现地址、端口、`session_id` 与 `path_mode` |
| 限制（必须写成条件成立，不得写成已具备能力） | GitHub **托管** runner 无入站端口，纯 P2P 直连通常不成立，打洞主要适用于自建 runner 或两端同 NAT 场景。因此：在托管 runner 上，预期结果就是走中继；`path_mode=direct` 只在实测通过的环境中出现，`[待真机确认]`，**本期不作为能力承诺** |
| 网页通道 | 浏览器侧打洞涉及 WebRTC 等未验证技术，`[待真机确认]`；**一期网页通道固定走中继**，不实现浏览器打洞，不做承诺 |
| 中继的角色 | 打洞失败时兜底；打洞成功时中继不参与数据面，只保留会话登记与到期管理 |

两条路径对判据的影响：

| 项目 | 打洞路径（`path_mode=direct`） | 中继路径（`path_mode=relay`） | 如何保证判据一致可判定 |
|---|---|---|---|
| 字段白名单 | 9 项全给：`relay_host` 填直连对端地址、`port` 填对端端口，`web_url` 填网页入口（网页仍走中继），`path_mode=direct` | 9 项全给：`relay_host` 填中继地址、`port` 填中继端口，`web_url` 填中继侧网页入口，`path_mode=relay` | 白名单不随路径变化，只换取值；`relay_host`/`port` 统一语义为「当前实际入口」。判据「9 项齐备且无掩码」对两条路径同一口径 |
| 判据一（会话建立且字段可用） | 同上，按 9 项判定 | 同上，按 9 项判定 | 判据正文只写「9 项齐备且原样可读」，不区分路径；路径差异只体现在取值 |
| 判据七（连接路径与回落） | 通过条件：日志出现 `path_mode=direct`，且直连对端地址与实际连接一致；用户提示为「直连已建立」 | 通过条件：打洞在超时内被判失败并出现 `path_mode=relay`，用户提示为「直连未建立，已切换到中继转发」；且 `session_id` 与阶段一相同 | 两条路径各有一条通过分支，任一分支证据齐全即判通过；托管 runner 上只验中继分支，direct 分支在自建 runner 环境取证，取证环境须写入报告 |
| 不得出现 | 任何凭据；中继侧在 direct 路径下不得留有会话状态 | 任何凭据；任何落盘会话 | 两条路径同一红线 |

## 七、技术栈与选型理由

| 类别 | 选型 | 理由 | 被否决方案与被否决理由 | 是否花钱或占用资源 |
|---|---|---|---|---|
| 语言（脚本） | Shell（P08） | runner 与 Ubuntu 20.04 自带，无额外运行时 | 否决 Python：需装运行时，增加依赖面；否决 Go：本期不自研中继 | 否 |
| 语言（前端） | TypeScript（P07） | xterm 类终端库以 TS/JS 生态为主，类型检查能约束 WS 消息形状 | 否决纯 JS：无类型约束；否决 Rust/WASM 前端：构建链过重 | 否 |
| 前端库 | xterm.js 类终端库（MIT 候选） | 浏览器内终端事实标准，键盘与转义序列支持成熟 | 否决自写终端渲染：工作量大且易错；否决 iframe 嵌入现成终端服务：引入第三方托管 | 否 |
| 工作流平台 | GitHub Actions（`ubuntu-latest`） | 需求方已有仓库在该平台，runner 即目标编译环境 | 否决 GitLab CI：需另建仓库与 runner | 是（Actions 分钟数） |
| 反连客户端 | `owenthereal/action-upterm`，固定 commit SHA | 现成反连步骤，参数可控 | 否决 `sshx`：托管第三方；否决自写反连：需自管重连与指纹 | 否 |
| 中转进程 | `uptermd` 官方二进制，仅作转发、准入能力关闭 | 与客户端同源，协议一致；免自研 | 否决自建 SSH 跳板：需自管路由回收；否决通用反代如 `nginx stream`：不能按动态 `session_id` 路由 | 否 |
| 中转形态 | 无状态字节转发，内存映射，重启即清 | 缩小中转被攻破后的价值：无凭据、无会话、无审计账本可窃 | 否决有状态中继（原 v2 思路）：需落盘会话、承担审计与限流，与用户新增硬要求冲突 | 否 |
| 访客认证（SSH） | runner 内嵌 sshd 验访客公钥 | 认证点与终端同处，中继彻底退出认证链 | 否决中继 `authorized_keys` 白名单：即中继做判定，与降级冲突 | 否 |
| 访客认证（网页） | WebAuthn 应用层挑战，runner 侧验签 | 判定留在 runner 侧；私钥不出设备 | 否决 mTLS 由中继验证：中继需持 CA 并判定，冲突；否决口令：可爆破 | 否 |
| 端口与 WS | 22 转发 SSH、443 转发 WS；系统 OpenSSH 迁 `127.0.0.1:22022` 或仅白名单来源 | 用户默认端口连入，降低使用成本 | 否决 all-in-one 高端口：使用成本高 | 否 |
| 限流与防护 | `nftables` + systemd + 内核参数 | 中继不做限流，安全控制下沉系统层 | 否决中继续做限流：与无状态定位冲突 | 否 |
| 静态托管 | GitHub Pages（候选） | 前端为纯静态文件，免费且与仓库同源 | 否决中继托管静态页：违反「只转发」；否决第三方对象存储：新增账号与费用 | **是，需按四类升级第 2 类放行**（对外发布） |
| 部署宿主 | 阿里云成都 ECS（资源基线第一条） | 既有机器，延迟与带宽满足交互式 TUI | 否决新购：无必要支出 | **是，需按四类升级第 1 类** |

## 九、风险与回滚

| 序号 | 风险项 | 触发条件 | 影响面 | 回滚步骤 | 回滚判据 | 责任人（岗位编号） |
|---|---|---|---|---|---|---|
| 1 | 端口冲突致宿主 SSH 失联 | uptermd 占 22 且系统 OpenSSH 未迁移 | 宿主不可运维 | 云控制台 VNC 登入，停 uptermd，恢复 sshd 到 22 | `ss -ltnp` 显示 22 由 sshd 监听且可登录 | O01 |
| 2 | 中继重启中断进行中会话 | 服务崩溃、部署重启、资源打满被重启 | 两个入口同时断开，作业内 TUI 操作丢失 | 不恢复会话，等待下一次显式触发重建 | 重启后映射为空、原信息重连被拒 | O01 |
| 3 | 路由抢占（降级直接代价） | `session_id` 泄漏后被他人抢先注册同键 | 真实用户无法进入，属可用性问题；但**真实身份仍由 runner 侧验证，不构成认证绕过** | 重新触发生成新 `session_id`；必要时轮换反连注册标识 | 新会话可正常注册与进入 | O01、S01 |
| 4 | 失去中继侧审计导致事后无法复盘 | 安全事件发生 | 无身份级证据链，只有系统层连接元数据 | 依赖 runner 作业日志（若仍存在）与系统层计数 | 能给出时间、源地址、`session_id` 三元事实 | S01 |
| 5 | 凭据泄漏到日志或仓库 | 参数误写、字段实现不当 | 会话可被他人接管 | 立即轮换 host key、TLS key 与反连注册标识，刷新仓库变量 | 旧指纹与旧密钥全部失效，日志无凭据 | S01、O01 |
| 6 | 资源打满 | 并发会话或大文件传输 | 3 Mbps 带宽与 2 GiB 内存不足 | 依 `MemoryMax` 兜底；必要时停会话 | 资源回到配额内，服务自恢复 | O01 |
| 7 | `uptermd` 无法关闭准入能力 | 实测发现其转发必须带 `authorized_keys` 校验 | 「中继不做判定」无法成立 | 改通用 WS/TCP 中继（需重新评估语言负责人），或退回 v2 有状态形态并经用户拍板 | 中继日志中不再出现准入判定记录 | M03、O01 |
| 8 | WebAuthn 在 runner 侧验签不可行 | 无可用验签工具链或 RP ID 无法绑定 | 网页通道认证无法按设计完成 | 退回 SSH 单入口，网页通道顺延 | 认证路径有可复现实现 | M03、P08 |
| 9 | 打洞误判或回落不彻底 | 判定条件过宽把不可用直连判成功；或回落时重建会话、更换 `session_id` | 用户按 `direct` 提示操作却连不上；或回落导致会话中断、需重新取连接信息 | 收紧判失败条件并提高超时；回落流程改为「保留原 `session_id`、只切换承载路径」；无法稳定则关闭打洞、固定 `path_mode=relay` | 在托管 runner 上稳定给出 `path_mode=relay` 且无需重新获取连接信息；关闭打洞后行为与 v2 一致 | P08、O01 |
